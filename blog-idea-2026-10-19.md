# SonicJs Blog Idea — 2026-10-19

**Angle:** Opinionated architecture deep-dive + implicit comparison (schema design / data modeling)

**Why this angle today:** Previous ideas covered agent-facing content APIs (May 20) and edge cache invalidation (May 21). The existing blog has comparisons, plugin and D1 deep-dives, and tutorials — but **nothing on how content is actually stored**. This is the biggest architectural differentiator SonicJs has and it's completely unwritten.

---

## 1. Title

**"One Table for Every Content Type: How We Stopped Migrating Our CMS Schema"**

(Alt titles: *"Your CMS Shouldn't Need a Migration Every Time You Add a Field"* · *"The Document Model: Schema-on-Read for Edge CMS"*)

## 2. Hook / Summary

Every time you add a collection in Strapi or Payload, your CMS writes a migration and bolts another table onto your database — which on Cloudflare D1 means a deploy, a schema drift risk, and a 100-column ceiling you'll eventually hit. SonicJs took the opposite route: a single `documents` table holding every content record, every media entry, and every version, with queryable fields exposed as indexed SQLite JSON generated columns that can be added without a migration file. This post makes the case for schema-on-read content storage at the edge, shows the SQL that makes it fast, and is honest about the three places it genuinely hurts.

## 3. Suggested Outline

1. **The migration treadmill** — Walk through what actually happens in a table-per-collection CMS when a non-developer asks for "one more field": codegen, migration, review, deploy, and a schema that diverges between local D1, preview, and production. Frame the real cost as *deploy coupling*, not disk layout.

2. **Schema-on-read, indexed-on-write** — Introduce the document model: one `documents` row per version, payload in a JSON column, plus `VIRTUAL` generated columns (`json_extract(data, '$.slug')`) that are indexed like any ordinary column. Show the `ALTER TABLE` and the `EXPLAIN QUERY PLAN` proving the index is used — this is the technical payoff of the post and the part readers will screenshot.

3. **What the JSON blob can't do (and the escape hatches)** — Multi-valued fields like `tags` can't be covered by a generated column, so they get a side table of indexed facet rows. Relationships get a typed edge table, which buys "where is this image used?" and reference-aware deletes — something a per-collection schema gets for free and a document model has to earn. Be explicit that these are concessions, not features.

4. **Versioning falls out for free** — Because every save is a row, draft and published are two independent booleans on the same root, not a status enum. A published page stays live while an editor saves five drafts; version numbers derive in SQL rather than JS so concurrent writers collide on a unique index instead of silently overwriting. Contrast with CMSs that bolt drafts on via a shadow table.

5. **The limits you will actually hit on D1** — The 100-column-per-table budget means generated columns are a finite resource you have to budget for; 100 bound params per statement forces chunked batch writes. Give the heuristic: promote a field to a generated column only when you filter or sort on it, otherwise leave it in the blob.

6. **When not to do this** — If your content shapes are stable, your team is all engineers, and you need ad-hoc analytical SQL across typed columns, table-per-collection is the simpler answer. The document model pays off when schemas churn, when plugins need to register types at boot, and when you can't afford a deploy per field.

## 4. Target Audience & Timeliness

**Audience:** Backend and full-stack developers evaluating or already running a headless CMS on serverless infrastructure — specifically people who've felt migration pain in Strapi/Payload/Directus, and developers building on Cloudflare D1 who are discovering its column and parameter limits the hard way.

**Why now:** D1 is past the novelty phase and teams are hitting real production constraints, so content about D1's *limits* and how to design around them is in short supply and high demand. Meanwhile the table-per-collection assumption is near-universal across the headless CMS field and essentially unchallenged in writing — there's an open lane for a technically credible contrarian post. And SQLite generated columns are a genuinely underused feature; a concrete, benchmarked example of JSON + generated columns + indexes is linkable content well beyond the SonicJs audience.
