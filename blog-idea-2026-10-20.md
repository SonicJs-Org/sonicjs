# SonicJs Blog Idea — 2026-10-20

**Angle:** Practical engineering / testing deep-dive (war-story flavored, with runnable code)

**Why this angle today:** Prior ideas were an opinion piece on agent-facing APIs (May 20), an edge-cache architecture deep-dive (May 21), and a storage/schema deep-dive (Oct 19). The live blog has comparisons, deep-dives, guides, and tutorials — but **zero content on testing**. Testing Workers + D1 is one of the most-searched, least-written-about parts of the Cloudflare stack, and it's a genuine lived problem in SonicJs (the project literally has a rule that mock-DB unit tests prove nothing about SQL).

## 1. Title

**"Your D1 Mocks Are Lying to You"**

(Alt titles: *"We Had 100% Test Coverage and Shipped 48 SQL Bugs"* · *"How to Actually Test Cloudflare D1 Without Deploying"*)

## 2. Hook / Summary

A mocked database makes your test suite green and your deploys terrifying. Every bug class that actually breaks a Cloudflare Workers CMS in production — wrong bind-parameter counts, non-atomic `batch()` writes, partial unique indexes that reject concurrent inserts, JSON generated columns that silently don't exist — is invisible to a mock, because a mock will cheerfully accept SQL that D1 would reject. This post shows how we replaced the lie with a real `better-sqlite3` D1 shim, what it caught the first day we turned it on, and the three D1 limits that *still* don't reproduce locally no matter what you do.

## 3. Suggested Outline

1. **The green-test trap.** What a typical hand-rolled D1 mock actually asserts: that your code called `.prepare()`. Not that the SQL parses, not that the binds line up, not that the constraint fired. A short gallery of real bug shapes that sailed through — a 14-placeholder `INSERT` with 15 binds, a `batch()` mixing ORM query-builder objects with prepared statements (which silently doesn't execute atomically), a write to a generated column that doesn't exist yet.

2. **Build the shim: `better-sqlite3` → D1 in ~80 lines.** Walk through implementing the D1 surface — `prepare().bind().first()/all()/run()`, `batch()` wrapped in a real transaction, `exec()` — on top of in-process SQLite. Emphasize the part people get wrong: `batch()` must be a transaction, or your tests pass while production leaves half-written rows.

3. **Run your real migrations in the test harness.** The single highest-leverage move: boot each test DB by executing the actual migration SQL files, not a hand-maintained fixture schema. This is what catches schema drift, missing indexes, and anything your ORM can't express (`VIRTUAL` generated columns, partial and expression unique indexes).

4. **Test the constraints, not the code paths.** Concrete assertions that only exist with a real engine: concurrent version inserts colliding on a partial unique index; a deliberate tenant-scope omission returning another tenant's row; a derived-row cleanup that `ON DELETE CASCADE` was assumed to handle (D1 doesn't guarantee FK enforcement — assume nothing).

5. **Route-level integration tests.** Mount the real Hono app against the shim and assert on HTTP responses. Faster than Playwright, and it covers the layer where auth, ACL, and SQL meet — the layer unit tests mock away on both sides.

6. **The three things local SQLite will never tell you.** D1's 100-bound-parameters-per-statement ceiling, the 100-columns-per-table ceiling, and real network/sub-request latency. None reproduce locally. Cover them with pure logic tests (chunk-size math, column budget assertions) and name them explicitly so the next person doesn't think the harness has them covered.

7. **Where mocks still earn their keep** — short, honest closer: pure projection/serialization logic, error branches, and anything with no SQL in it. The rule we landed on: *if a test's failure mode is SQL, it runs on a real engine.*

## 4. Target Audience & Timeliness

**Audience:** Developers building production applications on Cloudflare Workers + D1 — CMS/backend engineers, platform teams evaluating D1 for real workloads, and anyone who has written a `mockDb` object and felt uneasy about it. Secondarily, people evaluating SonicJs who want evidence of engineering rigor.

**Why now:** D1 is past the toy stage and is carrying real production data, which means the community has moved from "can I query it?" to "how do I not corrupt it?" — and the testing story is still the weakest documented part of the stack. Serverless SQL has no local emulator fidelity guarantee, so every team is independently rediscovering the same traps. This post is also strong trust-building content: it demonstrates competence by showing bugs rather than claiming their absence, which developer audiences reward far more than another feature tour. Bonus timeliness: AI coding agents generate plausible-looking SQL at volume, and a mock-only suite is exactly the wrong safety net for agent-written database code — worth one paragraph, as it reframes the post as current rather than merely good practice.

## Notes for the writer

- Lead with a real failure, not a thesis. The bind-count bug makes the best cold open: a bug that's arithmetic, obvious in hindsight, and literally impossible for a mock to catch.
- Code blocks should be copy-pasteable — the shim and one constraint test are the two artifacts readers will steal, and stolen code is the best distribution channel this post has.
- Keep the tone confessional rather than instructive. "We shipped these bugs" lands; "you should test properly" doesn't.
- Natural internal links: the D1 deep-dive and the plugin-architecture deep-dive. Natural follow-up post: the Playwright/E2E layer and why it stays out of the local loop.
